03 IAM (선수 학습, 약 2시간)

문서 유형: explanation

선수 학습 3/15. 앞선 문서를 전제하지 않는다. 처음 보는 사람 기준으로 씁니다.

이 문서를 왜 읽나

섹션 제목: “이 문서를 왜 읽나”

“이 서버가 저 데이터베이스의 비밀번호를 읽어도 되나?” — AWS 는 이런 질문에 매번 답해야 한다. 그 답을 정해 두는 곳이 IAM 이다.

IAM 은 AWS 의 출입 관리 시스템이라고 생각하면 된다. 누가(신원) 무엇을(권한) 할 수 있는지를 적어 둔다.

대회에서 대부분은 “역할을 하나 만들어 붙이면 끝” 이다. 그런데 2026 2과제 ③ 은 정책을 직접 써야 풀린다. 그래서 문법을 한 번은 봐야 한다.

① 학습 목표

섹션 제목: “① 학습 목표”
  • 사용자·역할·정책·신뢰 정책이 각각 무엇인지 한 문장으로 말한다
  • 인스턴스 프로파일이 EC2 에 권한을 주는 구조를 안다
  • 정책 JSON 의 Effect·Action·Resource·Condition 을 읽는다
  • ForAllValues: 같은 다중값 조건 연산자의 뜻을 안다

② 핵심 개념

섹션 제목: “② 핵심 개념”

네 가지 이름

섹션 제목: “네 가지 이름”
용어한 줄 정의
사용자(user)사람에 대응하는 장기 신원. 비밀번호나 액세스 키를 갖는다
역할(role)주인이 없는 신원. 필요할 때 누군가 빌려 쓴다(assume). 자격 증명이 임시다
정책(policy)“무엇을 할 수 있나”를 적은 JSON. 사용자·역할에 붙인다
신뢰 정책(trust policy)“누가 이 역할을 빌릴 수 있나” 를 적은 JSON. 역할에만 있다

역할에는 정책이 두 종류 붙는다는 것이 핵심이다.

인스턴스 프로파일

섹션 제목: “인스턴스 프로파일”

EC2 에 역할을 붙이는 껍데기다.

인스턴스 안에서 aws 를 부르면 SDK 가 인스턴스 메타데이터(169.254.169.254)에서 임시 자격 증명을 받아 온다. 리눅스 사용자와 무관하다 — ec2-user 든 root 든 같은 권한이다. 액세스 키를 홈 디렉터리에 넣으면 sudo su - 한 순간 권한이 사라지는 것과 대비된다. → 축 2

정책 JSON 읽기

섹션 제목: “정책 JSON 읽기”
필드뜻
EffectAllow 또는 Deny
Action어떤 API 를 부를 수 있나
Resource어떤 대상에 대해서인가 (ARN)
Condition그 요청이 만족해야 할 추가 조건

평가 규칙 하나만 외운다: 명시적 Deny 가 항상 이긴다. Deny 가 없고 Allow 가 하나라도 있으면 허용, 둘 다 없으면 거부(암묵적 거부)다.

조건 연산자에 붙는 접두사

섹션 제목: “조건 연산자에 붙는 접두사”

dynamodb:Attributes 처럼 값이 여럿인 조건 키에는 접두사가 붙는다.

접두사뜻
ForAllValues:요청의 모든 값이 허용 목록 안에 있으면 참
ForAnyValue:요청의 값 중 하나라도 허용 목록에 있으면 참

2026 요구는 “키 이름이 name 과 type 인 요청만 허용” 이다.

  • {"name","type"} → 둘 다 목록에 있음 → 참
  • {"name"} → 부분집합 → 참
  • {"name","price"} → price 가 없음 → 거짓 → 거부

ForAnyValue: 로 쓰면 {"name","price"} 도 name 때문에 통과해 버린다. 접두사 하나가 정답을 가른다.

③ 대회에서 어떻게 쓰이나

섹션 제목: “③ 대회에서 어떻게 쓰이나”
해요구
2023Bastion 에 PowerUserAccess
2024Bastion root 에서 AWS 전체 + EKS 전체 권한
2025각 Bastion 에 AdministratorAccess, EC2 에 AmazonSSMManagedInstanceCore
2026 1과제Bastion 에 Administrator 급, 앱 인스턴스에 secret 조회 + kms:Decrypt
2026 2과제 ③정책을 직접 작성 — 테이블 제한 + 속성 이름 제한

④ 미니 실습 (30분)

섹션 제목: “④ 미니 실습 (30분)”

  1. 역할 연습-role 을 만들고 신뢰 정책을 계정 전체로 연다.

  2. DynamoDB 테이블 연습-catalog 를 만들고(파티션 키 name), 위 ② 절의 정책을 연습-policy 로 만들어 역할에 붙인다.

  3. assume 해서 임시 자격 증명을 받는다.

  4. 세 가지를 시도해 결과가 갈리는지 본다.

  5. 끝나면 unset AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY AWS_SESSION_TOKEN 으로 되돌린다.

5번을 잊으면 이후 명령이 전부 제한된 권한으로 돌아 헤맨다.

⑤ 심화 개념

섹션 제목: “⑤ 심화 개념”

dynamodb:Select 를 넣으면 오히려 틀린다

섹션 제목: “dynamodb:Select 를 넣으면 오히려 틀린다”

AWS 문서는 GetItem 이 허용되지 않은 속성을 돌려주지 못하도록 "StringEqualsIfExists": {"dynamodb:Select": "SPECIFIC_ATTRIBUTES"} 를 함께 쓰라고 권한다. 그런데 2026 채점 3-7 은 --projection-expression 없이 get-item 을 호출한다. 이 조건을 넣으면 그 호출이 거부돼 항목이 실패한다.

문서 권장과 채점이 어긋나는 자리다. → 2과제 카탈로그 A-7

Resource 에 없으면 Deny 를 쓸 필요가 없다

섹션 제목: “Resource 에 없으면 Deny 를 쓸 필요가 없다”

secret 테이블 접근을 막으려고 Deny 문을 따로 쓰지 않는다. Allow 문의 Resource 에 catalog 만 적으면 나머지는 암묵적 거부다. 채점 3-6 이 “employee-policy 하나만” 붙어 있기를 요구하므로 문장을 늘리지 않는 편이 안전하다.

디버깅용 정책을 떼는 것을 잊지 않는다

섹션 제목: “디버깅용 정책을 떼는 것을 잊지 않는다”

권한 오류를 좁히려고 ReadOnlyAccess 를 임시로 붙였다면 반드시 뗀다.

⑥ 자기 점검 퀴즈

섹션 제목: “⑥ 자기 점검 퀴즈”

ForAllValues 와 ForAnyValue

ForAllValues:StringEquals 로 dynamodb:Attributes 를 ["name","type"] 에 묶었다. {"name","price"} 요청은?

  • 거부된다 — price 가 허용 목록에 없어 “모든 값” 조건이 깨진다
  • 허용된다 — name 이 목록에 있다

    그것은 ForAnyValue: 의 동작이다. ForAllValues: 는 전부 만족해야 한다.

  • 허용된다 — 조건은 읽기에만 적용된다

    조건은 그 Statement 의 모든 Action 에 적용된다.

  • 오류가 난다 — 조건 키를 잘못 썼다

    유효한 조건 키다. 정상적으로 평가되어 거부된다.

접두사 하나가 정답과 오답을 가른다. 2026 채점 3-9 가 정확히 이 요청을 보내 실패하기를 기대한다.

역할에 붙는 두 정책

employee-role 을 다른 계정 주체가 아니라 내 계정의 모든 user·role 이 assume 할 수 있게 하려면 어디를 고치나?

  • 역할의 신뢰 정책에서 Principal 을 arn:aws:iam::<계정>:root 로 둔다
  • 역할에 붙은 employee-policy 에 sts:AssumeRole 을 추가한다

    연결된 정책은 assume 한 뒤 무엇을 할 수 있나를 정한다. 누가 빌릴 수 있나는 신뢰 정책이다.

  • 각 사용자에게 employee-role 을 붙인다

    역할은 사용자에게 “붙이는” 것이 아니라 빌리는 것이다.

  • 역할을 public 으로 설정한다

    그런 설정은 없다.

신뢰 정책의 root 는 “계정 루트 사용자”가 아니라 “이 계정 전체”를 뜻한다. 자주 오해하는 표기다.
